# Behaviour

- The hub keeps disks in `disks.json` next to its config file, with the storage endpoint and tombstones of deleted disks. The storage server holds one file per disk and follows the hub: it creates, copies and grows files, and deletes those of deleted disks. Files it has no disk for are reported as orphans (`GET /api/storage`) and are never deleted.
- A disk is `creating` until the storage server reports its file at full size, `ready` after that, and `releasing` from detach or VM delete until the node confirms it no longer uses the disk. A releasing disk cannot be attached, grown or deleted. If the node stays offline, force the release (see [API](api.md)).
- A disk is `missing` when the connected storage server no longer has the file of a disk it reported before (lost volume, another storage server). It is never recreated blank; a missing disk cannot be attached (409). Restore the file to bring it back.
- A node starts a VM with disks only after the hub has confirmed that they are still wanted. It fails the VM with `storage not ready` while a disk's file has not been created yet, and with `storage unreachable` if an NBD server cannot be reached. A VM that is already running keeps working when the storage server restarts. On Linux nodes its disk writes wait until the server is back (for up to a week) and then continue, so nothing written is lost; they attach disks through `qemu-nbd` for this, while releases up to v0.5.0 used `nbd-client`, which lost every write after a storage restart without an error. On `vz` nodes a restart of a second or two is bridged the same way, but after a longer outage the disk can stay failed inside the VM (writes return I/O errors or hang, and the VM's disk shows the error on the hub) until the VM is restarted.
- On every boot, the guest formats a disk only if it is blank, mounts it at `mountPath` (found by `/dev/disk/by-id/virtio-<diskID>`) and grows the filesystem to the disk size. The first format makes the mount owned by `ubuntu`.
- The hub keeps SSH keys in `keys.json`, the network model (WireGuard keys, VM NICs, chassis, devices) in `network.json`, and VMs and nodes in `vms.json`, all next to its config file. The hub is the source of truth for VMs.
- The hub also lists its own user's default public keys (`~/.ssh/id_ed25519.pub`, `id_ecdsa.pub`, `id_rsa.pub`, …), read on each start. They cannot be deleted through the API and are preselected in the GUI.
- On connect and on every change, the hub pushes the desired VMs and their power state to the node. The node converges to it: it deletes VMs the hub does not know, creates missing ones and applies power. A VM that should run is restarted with backoff, and goes to `error` after repeated quick failures. This includes a `poweroff` inside the guest: the hub still wants the VM running, so the node boots it again. To keep a VM stopped, use **Shut down** or **Stop** (`POST /api/vms/{id}/shutdown` or `/stop`).
- The node stores each VM in `paths.vms/<id>/vm.json`. If a provisioned VM's directory is missing, it shows `error` ("VM directory missing"), and a start rebuilds it blank.
- Create, delete and power changes for an offline node are accepted and shown as `pending` until the node connects.
- Nodes join the gateway over a WireGuard underlay (`10.198.0.0/24`); OVN Geneve tunnels run on top of it. VMs get a management NIC on `10.200.0.0/16`, devices get addresses in `10.201.0.0/24`.
- The hub is meant for a trusted home network. Node↔hub traffic is plain `ws://` with a shared token, and the GUI and API, including device creation, have no user auth.
- The storage server's NBD port is unauthenticated: anyone who can reach `STORAGE_PORT` can read and write every disk. Changing the effective storage endpoint (also the client endpoint while the storage endpoint is empty) restarts every VM with disks, as their NBD URLs change.
- WireGuard devices can only reach the VMs' management IPs and the gateway DNS. The hub API and the OVN databases are firewalled from them.
- The hub stores device private keys, so configs can be downloaded again.
- VMs cannot reach each other on the management network; they talk only via shared networks (see [Networks](networking.md#networks)). The NAT NIC (the first NIC, for internet: vz NAT on Macs, the `vmm0` bridge on Linux nodes) is still shared.
- A released hub asks GitHub for the latest release at start, every six hours and on request (**Settings › Updates**), and keeps the answer in memory. A failed check only shows its error. Builds without a release version (`dev`) do not check.
- **Update node** makes the node download the hub's installer and run it in a process of its own (a transient systemd unit `vm-manager-node-update` on Linux, a separate session on macOS). The installer replaces and restarts the node, so its VMs restart with it. If the installer fails before that, the node keeps running the old version and reports the end of the installer output to the hub. Nodes started by hand cannot be updated this way.
- On `vz` nodes a disk can stay failed inside a running VM after a storage outage (writes hang or return I/O errors; the disk shows the error on the hub). When the storage server answers again and the disk has not reconnected within about ten seconds, the node restarts that VM, which gives it a working disk again.
- A hub started with `-stack` updates itself on request (**Settings › Updates**): it downloads the hub binary of the latest release, verifies it against `SHA256SUMS`, keeps the old binary as `<binary>.previous`, restarts in place and rebuilds its containers. Nodes reconnect; the VM network and attached disks are interrupted briefly while gateway and storage are replaced; VMs keep running. Linux nodes up to v0.5.0 lose disk writes when the storage server is replaced, so update nodes with attached disks before the hub. A failed build leaves the old containers running and is retried every minute. If the new hub does not start, put `<binary>.previous` back and restart the service.
